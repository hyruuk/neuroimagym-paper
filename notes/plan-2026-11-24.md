# fmri-gym → neuroimagym: docs rework, rename, principles

## Context

fmri-gym (tomov/fmri-gym, package `humans`) has outgrown its name: it runs games in fMRI, MEG and EEG sessions, and it is the hub of the Digital Brain Project (DBP) acquisition ecosystem: it defines the **rig file** every DBP toolbox reads, the **session script** format, the rig/gamepad tools, and the BIDS-like data layout. Its documentation is an 888-line README plus a QUICKSTART, a contributor rulebook (AGENTS.md + skills) and scattered READMEs, with 25 contradictions between them and the code; the only documentation written for experimenters lives in another repo (DBP_Welcome, branch `docs`, mkdocs-material) and re-documents fmri-gym features, already drifting.

Three outcomes wanted (2026-11-24):

1. **Rework the documentation entirely**: a network of Markdown files for human readers (high-level information, the list of functionalities, practical recommendations), rendered as a website.
2. **Rename the project to neuroimagym** (audit of 2026-11-13: `~/GitHub/humain/neuroimagym-rename.md`; nothing changed yet).
3. **Establish principles and guidelines** so that users, human and agent, make proper use of the tools, after a step back on neuroimagym's scope, workings and integration with the other DBP codebases.
4. **Start the methods paper** (added at the first review): the place where the general concepts are argued and the backbone, framework and vocabulary are decided now, with the future psych backend (classical tasks as step-based environments) in mind but not built; the documentation is designed so these additions iterate cleanly.

## Decisions (2026-11-24, with the user)

- **One `neuroimagym` command, a subcommand per tool, no alias**: `play` (fmri-play), `rig` with `--measure`, `rig report`, `rig pool` (rig-setup), `gamepad` (gamepad-calibration), `next-session` (fmri-ses), `record start|mark|stop` (session-logger), `parse-logs` (bids-from-logs; name picked by the user, tomov may prefer another). Not exposed: `python -m humans.standalone.photodiode` (the standalone flip-to-photon task behind `rig --measure`, which runs it when the rig declares a photodiode), `python -m humans.outputs.display` (developer self-test), `agents/agent_play.py`.
- **The session editor is dropped** (its own PR, needs tomov's agreement): sessions are hand-written scripts; the **scheduler** (Shrecki/scheduler) and **session-menu** (chrplr/session-menu) are documented as compatible managers of those `.sh` files; curricula are JSON validated at start-up.
- **Sessions, the neuroimagym way**: the native unit is the hand-written session script in the documented format; the managers handle its unfolding. Reconciling the script head with session-menu/the scheduler (`# runs` marker, `${SUBJECT:-…}`, a stable session number; #211 §4, session-menu#3) is a **later, separate PR**; the docs state the format as neuroimagym writes it and note the limitation.
- tomov agreed in principle to the rename: the rename PR goes to tomov/fmri-gym; tomov renames the repo right before the merge.
- Docs rendered with **mkdocs-material**, the DBP_Welcome recipe (HTML + PDF via `build_docs.sh`, offline build, print-site, Pages on main).
- **DBP_Welcome is reworked afterwards**, out of scope: neuroimagym's docs are complete on their own and DBP-agnostic; DBP appears once ("who uses it").
- British spelling (AGENTS.md's), present tense, one paragraph per line (AGENTS.md Rule 3). The name is free on GitHub and PyPI.
- **Focus now**: the rename, documenting what exists, and a way of documenting that iterates cleanly. Future work is kept in mind, not built: the **psych backend** (classical tasks as step-based environments; feasibility note of 2026-11-23) and the DBP_Welcome rework. The backbone, framework and vocabulary those need are decided now, in **the methods paper**.
- **The methods paper**: repo `hyruuk/neuroimagym-paper` (private for now), LaTeX only (`article` + `arxiv.sty`, arXiv preprint first, journal later), GitHub as `origin` where Claude edits, Overleaf as a second git remote (`overleaf`, local `main` ↔ Overleaf's `master`) where people render, comment and edit; merge-only sync, no force-push or history rewriting, feature branches on GitHub only, conflicts in `.tex` resolved only with the user. Scope in this plan: skeleton + outline + the Framework section drafted in full (it fixes the vocabulary the docs then follow).

## The step back: scope and boundaries

- **neuroimagym is** a general tool for any lab: any Gymnasium-compatible game played by a person in an fMRI, MEG, EEG or behavioural session, every frame, press, flip and trigger logged so a run replays exactly; plus the infrastructure a session needs: the rig file and its tools (form, measurement, gamepad calibration), the session-script format and its recording, the data layout and its conversion to BIDS, and the same curricula played by models.
- **It is not** a game, an analysis package, a session launcher for other programs, or the DBP procedure. Today it also carries DBP-specific content (the `dbp` extra, `configs/BC/`, the `dbp_meg` and `eyelink` rig sections read by no run here, `docs/DBP_*.md`): kept, labelled as team content; the DBP lists move toward DBP_Welcome in its rework.
- **Hub role**: the rig file is the single description of a setup and other programs read it (DBP_CogTasks_fMRI, DBP_MTB; divergently). The missing contract is a versioned JSON Schema + reference reader owned by neuroimagym (follow-up). The control vocabulary (`ControlNames`), the session-script dialect and the BIDS layout are also ecosystem contracts: the reference pages state them as such.
- **Boundary with DBP_Welcome**: neuroimagym documents its features (rig file incl. mock vs acquisition rig, measurement, controllers, sessions, data); DBP_Welcome keeps installation/pins, the multi-toolbox session conventions (as a profile on top of neuroimagym's format), the acquisition SOPs, one short page per tool linking into neuroimagym's docs. Links go DBP_Welcome → neuroimagym, never back.
- **Principles**: the code already enforces most of them (Appendix B); the docs make them visible to users and agents, in one page, with the practical recommendation attached to each.

### Future developments that shape the backbone now (not built here)

- **The psych backend** (`~/GitHub/DBP/dev/psych-backend-feasibility-2026-11-23.md`): PsychoPy scripts run unchanged as environments where one step is one `win.flip()` and the action is `(key, reaction time)`; a virtual clock for agents, tests and replay, a real clock for participants; verified on WCST (219 flips, 430 s of task time in 8.6 s; results CSV identical between real PsychoPy and a fake-renderer twin). It lands as `gym/psychopy_script/` + a thin `humans/adapters/psychopy.py`, one script = one `GamePhase`, `psychopy` as an extra, and one core change: **variable step duration** (the loop presents at the onset the environment reports and logs per flip). Decided there: one renderer for humans and agents (PsychoPy's own); milestone 1 replicates the four CogTasks exactly; goxpyriment programs depend on Pallier.
- **What the rename and the docs anticipate**, so it lands without renaming anything: the vocabulary of the paper's Framework section (environment, not game; the step as the unit; three stepping regimes, the third marked planned in the paper and absent from the docs until it exists); `docs/backends/` as a generic section where a `psychopy` page is one README + one generated nav line; `features.md`, `how-it-works.md` and `data/timing.md` structured by stepping regime; the principles page says "the same environment", not "the same game"; the rig-file reference marks which fields a script-based task reads; `GamePhase` / `"type": "game"` stay the present code's names (the docs say what the type plays).
- **The paper is where the general concepts are argued**: a common medium for humans and AI; more (active) naturalistic experiments; step-based environments translating between human time and engine time, operationalized for alignment and comparison; games step natively, other neuroimaging tasks are bounded by the refresh rate and input lag, so stepping them at the refresh rate (one step per flip) makes them like the games; logging; multimodal integration; the modular approach.
- DBP_Welcome's rework and the DBP procedures: later; only the follow-up list here.

### `docs/overview/principles.md` (outline; each item = statement / why / do)

A. The rig file is the one description of a setup: one per setup in `configs/<team>/rigs/`, read by every run and by other programs; notes are for people, programs read settings; every run files the whole rig in its manifest. B. Two rigs per setup, chosen on purpose: a mock rig for trying/developing/training, an acquisition rig made and measured at the scanner on the stimulus computer (real screen, geometry through the mirror, devices, trigger line, photodiode: "close enough" is wrong in ways nobody notices); `RIG=` is the switch, look at it before every acquisition. C. No default that can change a recording: no default rig, controls, `fps`, trigger setup; a default that applies is printed at READY and in the manifest, never on the participant screen. D. Never run with an invisible problem: checks run at the desk with the fix in the message, fix the cause; `--dummy-trigger`/`--skip-load-games` are test switches that announce themselves, never for an acquisition; a stopped run is recorded (`run_end.how`, exit 3) and `set -e` stops the script: decide and write down. E. Measure, don't assume: long measurement once per rig and after any hardware/driver/OS change, quick one before each session; sticks calibrated on the machine they are used on; the measurement never raises, read the verdicts. F. What goes where: curriculum (what, same everywhere) / rig (how, this setup) / run (subject, session, run, duration from the script); neither file names the other; `next-session` is the only command that reads the disk for a number. G. One run is one process; a session is a plain script that any shell plays, written by hand in the documented format and kept under `configs/<team>/subjects/`; the scheduler and session-menu are compatible managers; runs are numbered per task by their place, a skipped line keeps the numbering. H. Nothing is ever overwritten; the numbers come from the design: reruns go to `_02` with the same seeds; calibrations, recordings, measurements are new files; never touch a data folder by hand. I. Reproducibility is the product: everything logged, bit-exact replay, provenance (`-dirty`) in every manifest; acquire from a clean checkout at a known commit, rerun the demo and the quick measurement after an update. J. Humans and models play the same game: game logic in the env, a model sees only what the participant saw, pin seeds for comparisons. K. Keep the hot path lean: nothing runs inside a run but the run; tools are separate commands; nothing else on the stimulus computer during an acquisition; measure with screen capture on if it is on. L. Install only what you need, and name all of it (`uv sync` installs exactly the named extras). M. Machine facts stay on the machine (calibrations, measured latencies); measure again rather than copy. N. The experimenter's keys (RETURN starts, CTRL+ESCAPE stops, F-keys and modifiers reserved; ESCAPE alone does nothing); the participant screen shows no diagnostics. O. Data hygiene and privacy: a session recording holds everything typed; `parse-logs` refuses an ambiguous attempt. P. The documentation keeps these rules: one fact in one place, normal path first, present tense, every command tested.
**If you are an AI assistant operating these tools**: read this page, concepts, run-a-session, troubleshooting first (AGENTS.md only to change code); never choose a rig, subject label, session or run number yourself, take them from the script or ask, use `next-session` for a new session; never pass `--dummy-trigger`/`--skip-load-games` unless told it is a test, never put them in a committed script; never create, delete, rename or edit anything under a `data_root`, `measured/` or the calibration folder; write sessions in the documented script format and keep the header and recording lines as documented; when a check fails, report the message and the fix, never silence it by editing a rig or curriculum without saying what and why; before an acquisition, state what you verified (`RIG=`, the quick measurement, the sync line at READY).

AGENTS.md stays the contributor rulebook: title; one sentence in "Where things are explained" ("Using the tools is `docs/`; an agent asked to set up, run or debug a session reads `docs/overview/principles.md` first"); Rule 3 gains #211's writing rules (one fact in one place; normal path first, caveats to troubleshooting; one idea per paragraph; a how-to opens with what it does and what you will have; commands in docs are tested); `DEPENDENCIES.md` pointer → `docs/contributing/architecture.md`. Skills stay procedures; the troubleshooting skill keeps the agent's reading procedure and points to `docs/troubleshooting.md` (the human page is the source; "neither in both" holds because site pages that show a skill are includes).

### Vocabulary (stated in concepts.md, repeated in the glossary)

**backend** = the integration of one game engine (the `backend` key; never platform/family/engine for it); **engine** = the program running the game; **env** = the Gymnasium env an adapter wraps. **curriculum** = the file a run plays (never "config" in prose); **run** = one curriculum played once by one participant: one command, one process, one folder. **phase** (entry of a curriculum) / **block** (a game phase as played; the block folder) / **episode** / **level** (a game's level, the `levels/` folder); "played until won", never "blocking". **participant** in prose, **subject label** for `sub-…`. **controls** (what a curriculum binds), **key** (keyboard), **button** (controller); curricula READMEs' "## Keys" → "## Controls". **sync** (how a run starts), **trigger** (the pulse/key that starts a run), **codes** (what is sent to a MEG/EEG recording); **acquisition** for the recording as a whole, "scanner" only for MRI. **rig** always; **rig measurement** for `--measure`; **mock rig** vs **acquisition rig**. **session script** (glossary: "also called master script"); **experimenter** at the console.

### How the docs iterate cleanly

### B. Architecture and concepts (upstream main 9a58bfd)
